CRITICAL: FIELD NAMING vs TYPE NAMING (PYDANTIC SHADOWING TRAP)
═══════════════════════════════════════
If a field name is IDENTICAL to a Python type name (date, type, id, list,
str, int, bool, time, datetime), you MUST use ONE of these two techniques
to avoid a silent Pydantic bug where the field becomes "must be None":

TECHNIQUE 1 (PREFERRED) — Add this as the VERY FIRST line of the file:
    from __future__ import annotations

TECHNIQUE 2 — Use fully qualified type names:
    import datetime
    ...
    date: Optional[datetime.date] = None      # NOT: date: Optional[date]

WHY THIS MATTERS:
In a class body, Python evaluates the assigned value BEFORE resolving the
annotation. So `date: Optional[date] = None` becomes `Optional[None]` which
Pydantic interprets as "this field must be None". The code LOOKS correct
but silently rejects any real date value at runtime.

RULE:
- If ANY field in the schema has a name matching a type (date, type, id...),
  add `from __future__ import annotations` as the first import.
- This has zero downside and prevents an entire class of runtime bugs.
- Apply this rule PROACTIVELY, even when in doubt.
